# TESTES E VERIFICAÇÃO

## Objetivo desta pasta

Esta pasta serve para organizar os testes realizados à aplicação, verificar se as funcionalidades estão a funcionar corretamente e registar os resultados obtidos.

Os testes permitem encontrar erros e confirmar se a aplicação cumpre os requisitos definidos para o projeto.

## O que deve ser colocado aqui?

### 1. Plano de testes de aceitação

Documento que descreve os testes que serão realizados para confirmar se a aplicação cumpre os requisitos e corresponde ao que foi definido.

**Responsável principal:** Analista / Arquiteto de Sistemas.

### 2. Testes unitários

Testes que verificam se pequenas partes do código funcionam corretamente, como funções, métodos ou algoritmos individuais.

**Responsável principal:** Programador.

### 3. Testes dos requisitos funcionais

Testes que verificam se cada requisito funcional está implementado corretamente.

Exemplos:
- **RF1:** verificar se a autenticação funciona.
- **RF3:** verificar se é possível escolher uma grelha entre 10 e 20.
- **RF4:** verificar se é possível selecionar a dificuldade.
- **RF5:** verificar se a aplicação permite escolher um tema.
- **RF7:** verificar se é possível guardar o progresso e continuar mais tarde.

**Responsável principal:** Analista / Arquiteto de Sistemas, com a colaboração do Programador na preparação e execução dos testes.

### 4. Registo dos resultados

Documento que apresenta os testes realizados, os resultados obtidos, os erros encontrados e as correções efetuadas.

**Responsável principal:** Analista / Arquiteto de Sistemas, com a colaboração do Programador no registo e na resolução dos erros.

### 5. Revisão do código

Verificação do código desenvolvido para identificar erros, melhorar a organização e confirmar que respeita as decisões técnicas do grupo.

**Responsável principal:** Programador, com a participação do Analista / Arquiteto de Sistemas.

## Regras de organização

- Cada teste deve indicar o que pretende verificar.
- Os resultados devem corresponder aos testes realmente realizados.
- Os erros encontrados devem ser registados e acompanhados até à sua resolução.
- Os testes devem ser repetidos quando uma alteração puder afetar uma funcionalidade.
- Não se deve indicar que um teste foi aprovado sem o ter executado.

## Resultado esperado

No final, esta pasta deve permitir demonstrar que a aplicação foi testada, que os resultados foram registados e que os problemas identificados foram analisados e corrigidos.
